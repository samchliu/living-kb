一份文件可信到什麼程度，看它的知識狀態：

## REQ-001：每日商品推薦

> REQ-001 · requirement · 權威 · active · 負責人 PM · 更新 2026-09-04 · requirement.md
> 關聯：derived_from EXP-001 · derived_from PROTO-003 · derived_from FB-001 · derived_from FB-002 · derived_from FB-003 · verified_by `tests/e2e/recommendations.spec.ts`
> 被引用：CR-001 (changes) · ADR-001 (decides_for) · BR-001 (derived_from) · FB-004 (evidence_for) · API-001 (implements)

> 由需求探索 Agent 於 2026-07-08 根據 EXP-001、PROTO-001..003、FB-001..003 起草。PM 於 2026-07-15 編修並核准。

#### 問題

店長都是在客人問起時才發現商品缺貨，要到商品過期或需要出清時才發現庫存過多。POS 與庫存資料都存在，但在忙碌的早上太原始、無法直接行動。*（FB-001、FB-002）*

#### 目標

每位試點門市店長每天早上開店前，都能拿到一份簡短、值得信任的清單，告訴他該補什麼、該推什麼。

成功指標（試點，8 週）：店長每 7 天中至少有 4 天打開清單；≥ 50% 的推薦被標記為「已處理」。*（目標由 PM 設定，尚未驗證。）*

#### 使用者

| 使用者 | 需要 |
|---|---|
| 店長（試點：03、07、11 店） | 知道今天要補什麼貨、推什麼商品，以及原因 |
| 老闆 | 看到資料真的有被使用（使用率數字） |

#### 範圍

#### 1. 要求的變更

> 「把推薦區間從 30 天改成 14 天。」
> —— 老闆，2026-08-28，傳給 PM 的訊息

#### 原因

正式環境回饋 **FB-004**：07 店的月餅禮盒在系統建議補貨之前就賣完了。30 天平均掩蓋了需求暴增（每天約 1 盒 → 約 9 盒）。RD 的數據顯示，14 天區間大約可以提早一天觸發補貨。

##### 相互作用的規則——真正重要的發現

**BR-001#R2** 要求*區間內*至少賣出 **5** 件。這個門檻是針對 30 天校準的（≈ 每天 0.17 件）。改成 14 天後，同樣的 5 件代表 ≈ 每天 0.36 件。

每天銷量約在 0.17 到 0.36 件之間的商品，會**完全不再被納入考量**。而這些滯銷品，正好就是**促銷（庫存過多）**的候選商品。

以試點門市最近 14 天的資料重跑（RD，2026-08-30）：

| 情境 | 每店每日補貨推薦數 | 每店每日促銷推薦數 |
|---|---|---|
| 目前（30 天，最低 5 件） | 2.9 | 1.8 |
| 照原要求（14 天，最低 5 件） | 3.6 | **0.4** |
| 14 天，最低 3 件 | 3.6 | 1.6 |

照字面執行這個變更，會修好 FB-004 的問題，卻幾乎消滅了庫存過多的推薦——這是沒有人要求的行為改變。**這是 PM 要決定的商業問題**，不是技術問題；Agent 不替人選擇。

**BR-001#R7**（最低歷史 14 天）：與 14 天區間一致。`[inferred]` 檢查時，Agent 發現了一個**既有的偏移**：對於有 14–29 天歷史的門市，`scoring.py:41` 除以 30 而不是實際可用天數，低估了銷量。BR-001 沒有定義這個情況。改為 14 天區間後，這個情況就不會再出現。記錄備查（RD）。

##### 效能

彙總查詢：掃描的資料列約減少 50%；每日排程工作時間預期略為縮短。API 不受影響（預先計算）。未發現風險。

##### 風險／副作用

- 低銷量商品的推薦雜訊變多（單筆大量購買就可能觸發補貨）。
- 店長可能會注意到清單一夜之間改變 → PM 需通知試點店長。
- 季節性處理只解決了一部分；正式的解法可能是另一條規則（REQ-001 Q2）。

## BR-001：每日推薦規則

> BR-001 · business-rule · 權威 · active · 負責人 PM · 更新 2026-09-04 · business-rule.md
> 關聯：derived_from REQ-001 · derived_from FB-002 · derived_from FB-003 · implemented_in `services/recommendation/scoring.py` · implemented_in `jobs/daily_recommendations.py` · implemented_in `sql/recommendation_window_agg.sql` · verified_by `tests/recommendation/test_scoring.py` · verified_by `tests/e2e/recommendations.spec.ts`
> 被引用：CR-001 (changes) · ADR-001 (decides_for) · FB-004 (evidence_for) · API-001 (implements)

> **權威。** 如果程式碼、原型或任何人的記憶與本文件不一致，那是要回報的衝突——而不是悄悄修改任何一方的理由。

#### 規則

| # | 規則 |
|---|---|
| R1 | 門市的推薦**必須**依據該門市截至昨日為止、**回溯區間**內的 POS 銷售資料計算。 |
| R2 | 商品在區間內至少要賣出 **min_sales_in_window** 件，才會被納入考量。 |
| R3 | `庫存可售天數 = 現有庫存 ÷（區間內銷量 ÷ 回溯區間天數）`。若 `庫存可售天數 < restock_threshold`，商品為**補貨（RESTOCK）**；若 `庫存可售天數 > overstock_threshold`，則為**促銷（PROMOTE）**。 |
| R4 | 每間門市每天最多 **max_recommendations** 則。補貨項目排在前面（可售天數最低者優先），接著是促銷項目（可售天數最高者優先）。 |
| R5 | ERP 中標記為*停售*或*供應商無法供貨*的商品**不得**被推薦。 |
| R6 | 每則推薦**必須**附上理由，且理由至少包含一個依 R1–R3 計算出的數字事實。理由**不得**包含任何不在計算結果中的數字。 |
| R7 | POS 資料少於 **min_history** 天的門市**不得**產生推薦；App 顯示「資料還不夠」。 |
| R8 | 推薦**必須**在**門市當地時間 06:00 前**可用，使用前一日結帳後的 POS 資料與每晚的庫存快照。 |

#### 參數

| 參數 | 值 | 使用於 | 備註 |
|---|---|---|---|
| `lookback_window` | **14 天** | R1、R3 | v1.1 之前為 30 天（CR-001） |
| `min_sales_in_window` | **3 件** | R2 | v1.1 之前為 5 件（CR-001）——與區間大致維持相同比例（≈ 每天 0.2 件），讓滯銷品仍有資格被列為促銷 |
| `restock_threshold` | 3 天 | R3 | |
| `overstock_threshold` | 30 天 | R3 | |
| `max_recommendations` | 5 | R4 | |
| `min_history` | 14 天 | R7 | 現在等於 `lookback_window`——一定有完整區間可用 |

#### 理由

| 規則 | 為什麼 | 證據 |
|---|---|---|
| R1 | 近期銷售反映目前需求；14 天能在幾天內反應季節性暴增，同時平滑單日雜訊 | FB-004、CR-001 |
| R2 | 避免因為 1–2 筆偶然的銷售就做出推薦 | RD 分析 2026-07-10；於 CR-001 重新校準 |
| R3 | 店長思考的方式是「還有幾天會賣完」 | FB-002（「賣了 90 個、只剩 8 個」） |
| R4 | 「幾則就好」——再多就不會看。**5** 是 PM 於 2026-07-15 選定的「幾則」上限；它在 PROTO-003 中只是意外出現，**未**被當作證據。 | FB-003 I3 |
| R5 | 推薦一個訂不到的商品會摧毀信任 | PM 決定，2026-07-15 |
| R6 | 店長不理解原因就不會行動；LLM 文字不得捏造數字 | FB-002、ADR-001 |
| R7 | 在不完整區間上取平均會誤導 | RD，2026-07-10 |
| R8 | 店長在開店前查看（最早 08:00） | FB-003 I2 |

#### 適用條件

適用於試點門市 03、07、11（REQ-001 範圍）。所有商品類別。每間門市每天計算一次。

#### 例外

目前沒有核准的例外。*（季節性商品是未解問題——REQ-001 Q2。）*

| E2 | 14 天賣出 7 件（每天 0.5 件），庫存 40 件 → 可售 80 天 | 促銷 | R3 |

## ADR-001：規則式評分 + LLM 撰寫說明文字

> ADR-001 · adr · 權威 · active · 負責人 RD · 更新 2026-09-02 · adr.md
> 關聯：decides_for REQ-001 · decides_for BR-001 · implemented_in `services/recommendation/scoring.py` · implemented_in `services/recommendation/explain.py` · implemented_in `prompts/recommendation_explanation.md`
> 被引用：FB-004 (evidence_for) · API-001 (governed_by) · CR-001 (relates_to)

> **每個重要的技術決策都應該有可追溯的理由。**
> 已接受的 ADR 不會被改寫。備註追加在最下方。

**決策者：** RD
**決策日期：** 2026-07-17

#### 背景

REQ-001 需要每日的補貨／促銷推薦，並附上店長會信任的**數字理由**（FB-002）。老闆要的是「AI 推薦」（EXP-001），而店長明確表示不信任黑盒子（FB-002 I3）。

當時的事實：
- 約 5 個月的 POS 歷史資料，12 間門市；每晚的 ERP 庫存快照。
- 3 間門市的試點必須在 8 月中上線——約 4 週的開發時間。
- 團隊：1 位 RD。
- BR-001#R6：理由只能包含計算出來的數字。

#### 決策

我們將以**基於 SQL 彙總資料的確定性規則**（BR-001）計算推薦，並**只用 LLM 來描述理由**，輸入是一組結構化的計算事實。如果生成的文字包含任何不在事實中的數字，就捨棄它，改用範本句子。

#### 替代方案

| 方案 | 摘要 | 為什麼沒選 |
|---|---|---|
| **A（採用）** | 規則 + LLM 描述計算出的事實 | — |
| B | ML 需求預測模型 | FB-001 已降低預測的優先順序；5 個月的資料不足以學到季節性；難以解釋；4 週內做不完 |
| C | LLM 直接讀銷售資料並做推薦 | 無法保證數字正確（違反 BR-001#R6）；不確定性高；難以測試；每店每日的成本 |
| D | 規則 + 固定範本文字，不用 LLM | 可行且最簡單。在 PROTO-003 審查時範本文字讀起來很生硬，因此不作為主要方案，但保留作為**備援** |

#### 後果

**正面**
- 每則推薦都能從資料中解釋與重現。
- BR-001 與程式碼、測試一一對應。
- 便宜：每則推薦一次小型 LLM 呼叫，每店每天最多 5 則。

**負面**
- 規則的反應速度受限於回溯區間；季節性暴增處理得不好。
- 門檻是手動調整的，不是學出來的。
- 「AI」只存在於措辭中——老闆應該知道這一點（PM 已告知，2026-07-17）。

**需要的後續行動**
- LLM 輸出的數字驗證防護（BR-001#R6）。
- 記錄「已處理」／「先不要」以衡量準確度（REQ-001 Q1）。

#### 取捨

| 我們得到 | 我們放棄 |
|---|---|
| 可解釋性、可測試性、上線速度 | 預測準確度、對季節性的自動適應 |

**重新檢視條件：** 累積 ≥ 12 個月歷史資料且涵蓋 ≥ 10 間門市，**或**店長反覆回報推薦太慢或錯誤。

## API-001：GET /stores/{storeId}/recommendations

> API-001 · api · 權威 · active · 負責人 RD · 更新 2026-09-04 · api.md
> 關聯：implements REQ-001 · implements BR-001 · governed_by ADR-001 · implemented_in `services/recommendation/api.py` · implemented_in `web/src/features/recommendations/` · verified_by `tests/recommendation/test_api.py`
> 被引用：CR-001 (changes)

#### 端點

| 欄位 | 值 |
|---|---|
| Method | GET |
| Path | `/api/v1/stores/{storeId}/recommendations` |
| 驗證 | Session token；使用者必須是 `storeId` 的店長（或老闆角色） |
| 使用端 | Web app（手機瀏覽器） |
| 穩定度 | stable |

#### 目的

回傳某間門市今日預先計算好的推薦（REQ-001）。唯讀；計算在每日排程工作中完成（BR-001#R8）。

#### 請求

| 參數 | 位置 | 型別 | 必填 | 說明 |
|---|---|---|---|---|
| `storeId` | path | string | 是 | 例如 `S07` |
| `date` | query | `YYYY-MM-DD` | 否 | 預設為門市當地時間的今天 |

#### 回應

| 欄位 | 型別 | 說明 | 規則 |
|---|---|---|---|
| `status` | `ready` \| `insufficient_data` \| `not_generated` | | R7、R8 |
| `data_window` | `{from, to, days}` | 實際使用的區間。**UI 必須顯示這個值，而不是寫死的數字。** | R1 |
| `items[]` | array，≤ 5 | 已排序 | R4 |
| `items[].type` | `restock` \| `promote` | | R3 |
| `items[].stock_on_hand` | int | 來自每晚快照 | R3 |
| `items[].avg_daily_sales` | number | 區間銷量 ÷ 區間天數 | R3 |
| `items[].days_of_cover` | number | 庫存可售天數 | R3 |
| `items[].reason.facts` | object | 文字唯一可以使用的數字 | R6 |
| `items[].reason.text` | string | LLM 撰寫或範本備援 | R6 |
| `items[].reason.source` | `llm` \| `template` | | ADR-001 |

```json
{
  "store_id": "S07",
  "date": "2026-09-10",
  "status": "ready",
  "data_window": { "from": "2026-08-27", "to": "2026-09-09", "days": 14 },
  "generated_at": "2026-09-10T05:12:44+08:00",
  "items": [
    {
      "rank": 1,
      "product_id": "P-88231",
      "product_name": "奶黃月餅禮盒（6 入）",
      "type": "restock",
      "stock_on_hand": 12,

      }
```

#### 錯誤

| 狀態碼 | 錯誤代碼 | 何時發生 | 用戶端應該 |
|---|---|---|---|
| 400 | `INVALID_DATE` | `date` 格式錯誤或是未來日期 | 顯示錯誤 |
| 401 | `UNAUTHENTICATED` | 沒有 session 或已過期 | 導向登入 |
| 403 | `FORBIDDEN_STORE` | 使用者不是這間門市的店長 | 顯示「無權限」 |
| 404 | `STORE_NOT_FOUND` | 不存在的 `storeId` | 顯示錯誤 |

`insufficient_data` 與 `not_generated` 是 `items` 為空的 **200** 回應——它們是正常狀態，不是錯誤。
