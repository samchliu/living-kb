# 事實來源政策（Source of Truth Policy）

每個主題都恰好有一個權威來源。當來源之間不一致時，**AI 回報衝突——而不是自己挑一個贏家。**

---

## 權威對照表

| 主題 | 事實來源 | 不是事實來源 |
|---|---|---|
| 產品範圍 | 已核准的**需求**（`REQ`，status approved/active） | 原型、回饋、聊天訊息、程式碼 |
| 商業規則 | 已核准的**商業規則**文件（`BR`） | 程式碼、原型、某人的記憶 |
| 架構決策 | **ADR**（已接受、未被取代） | ARCH 圖、程式碼結構 |
| 目前的架構 | **ARCH** 文件，並與程式碼交叉比對 | 舊簡報 |
| API 合約 | **API 規格**（若有機器可讀規格則以它為準，否則為 `API` 文件） | 實作實際回傳的內容 |
| 實作行為（系統*現在實際上*做什麼） | **原始碼**（及其測試） | 文件 |
| 維運程序 | **OPS** 文件 | 口耳相傳的知識 |
| 需求為什麼存在 | **探索／回饋**，作為被 REQ 引用的*證據* | — |
| 誰負責什麼 | **OWNERSHIP.md** | `authors` 欄位、git blame |

請注意「系統**應該**做什麼」（REQ、BR、API 規格——由人負責）與「系統**實際**做什麼」（程式碼）之間的區分。兩者在各自的意義上都是真的。當它們不同時，就是**偏移（drift）**，由人來決定要修正哪一邊。

## 優先順序規則

1. **權威一律勝過探索性。** 一個顯示 10 則推薦的原型，不會凌駕於寫著 5 則的 BR 之上。
2. **生效中勝過已棄用。** 被取代的 ADR 是歷史，不是指引。
3. **較具體的只有在明確說明時才勝過較一般的。** 如果 `BR-003` 是 `BR-001` 的例外，其中一份必須寫明。否則就是衝突。
4. **較新的不會自動勝過較舊的。** 較新的草稿在核准之前不是權威。
5. **程式碼永遠不會默默勝出。** 「程式碼做了 X，所以 X 一定是規則」正是 AI 絕對不能做的推論。

## 當來源衝突時

AI 必須：

1. **停下來**——不要為了讓雙方一致而編輯任何一方。
2. **回報**雙方來源，附上引文與位置。
3. **分類：**
   - `CONFLICT`（衝突）——兩份權威文件不一致
   - `DRIFT`（偏移）——權威文件與實作不一致
   - `AUTHORITY LEAK`（權威外洩，歸在 CONFLICT 下回報）——權威文件或程式碼把探索性知識當成依據
4. **指名**雙方的負責人。
5. **建議**可能的解決方式，但不替人選擇。

```text
CONFLICT (@pm, @rd)
  BR-001#R3：  「每間門市每天最多顯示 5 則推薦（MUST）」
  API-001：    回應範例與 handler 最多回傳 10 筆
               （services/recommendation/api.py:57  LIMIT = 10）
  可能的解決方式：
    a) 程式碼錯了 → 修正 LIMIT，並為 BR-001#R3 補上測試
    b) 規則改了 → 開 CR 更新 BR-001，再更新 API-001
  我沒有修改任何東西。
```

## `source_of_truth` 後設資料欄位

| 值 | 意義 |
|---|---|
| `self` | 本文件就是這個主題的權威來源 |
| `<路徑>` / `<id>` | 本文件負責說明；權威來源在別處（例如 `api/openapi.yaml`） |
| `none` | 探索性——永遠不是權威來源 |
