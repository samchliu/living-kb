# 負責歸屬政策

> **負責人 ≠ 撰寫者。** 負責人對正確性負責。AI、PM、RD、QA 或其他任何人都可以建立或修改文件。

團隊名冊與領域對照表在 [`OWNERSHIP.md`](../OWNERSHIP.md)。本政策定義「負責」的意義。

---

## 負責人做什麼

| 職責 | 實際上 |
|---|---|
| **對正確性負責** | 文件錯了，負責人就是要修正它、或確保它被修正的人。 |
| **核准權威內容的變更** | 在 PR 上給予 approve，或明確核准並記錄在 `approved_by`。 |
| **定期審查** | 確認內容仍然正確時更新 `last_reviewed`（而不是只要編輯就更新）。 |
| **回答問題** | AI 的上報與健康報告都會指名給負責人。 |
| **解決或轉交衝突** | 當自己的文件與別人的文件衝突時，與對方負責人協調解決。 |

負責人**不必**親自撰寫文件。實務上很多文件會由 AI 起草。

## 預設負責人

| 知識 | 負責人 |
|---|---|
| 產品背景、探索、原型、回饋 | PM |
| 需求、變更申請 | PM |
| 商業規則 | PM |
| 架構 | RD |
| ADR | 決策者（在 ADR 中列名） |
| API 與資料合約 | RD |
| 維運 | DevOps / RD |

## 規則

1. **每份文件恰好一個負責角色。** 共同負責等於沒人負責。必要時就把文件拆開。
2. **負責人必須是人。** `owner: AI` 無效，健康 Agent 會回報。
3. **負責人必須在名冊中。** 不在 `OWNERSHIP.md` 中的負責人會被回報為 `OWNERSHIP`。
4. **明確轉移負責權。** 在一個由新負責人核准的 PR 中修改 `owner` 欄位。
5. **負責人不在時。** `OWNERSHIP.md` 中的代理人可以讓文件保持最新，但除非負責人明確授權，否則不應核准權威內容的變更。
6. **跨領域變更需要雙方負責人。** 同時修改 BR（PM）與 API（RD）的 PR，需要兩人各自核准自己的部分。

## 什麼算是核准

刻意保持輕量：

- 負責人在 PR 上的 approve，**或**
- 負責人說「核准」的留言／訊息，並在變更歷史中連結或引用。

沒有簽核表單，沒有會議。唯一的要求是它被**記錄下來**（誰、何時），以便日後追溯。
