# AI 政策

> **AI 不是知識的負責人。AI 是一層持續理解、連結、驗證，並協助維護「由人負責的知識」的機制。**

本政策適用於所有讀寫這個知識庫的 AI 系統：程式助理、聊天助理、CI 機器人，以及 [`agents/`](../agents/) 中規格定義的 Agent。

---

## AI 可以（MAY）

| 行為 | 條件 |
|---|---|
| **建立任何類型文件的草稿** | `status: draft`；`authors` 包含 `AI`；`owner` 是人類角色 |
| **修改文件** | 探索性文件：負責人要求時可直接修改。權威文件：以提議的 diff（PR 或建議）交由負責人核准。連結、錯字、格式、後設資料修正：可直接修改。 |
| **摘要** | 會議、回饋、PR 討論、決策歷史 |
| **連結知識** | 新增或提議 `related` 連結；建立可追溯性視圖 |
| **分析影響** | 為提議中的變更與 CR 產出影響分析 |
| **偵測不一致** | 衝突、偏移、斷裂連結、缺漏文件、歸屬缺口 |
| **偵測過期知識** | 依據 `last_reviewed`、`review_every`，以及相關程式碼／文件的變更 |
| **產生原型** | 一律標示為探索性；一律附上內建假設清單以及做假／模擬的部分 |
| **從探索中產生需求——以提案形式** | 產出為*候選* REQ/BR，`status: draft`，每個主張都引用證據，並列出未解問題 |

## AI 不得（MUST NOT）

| 禁止事項 | 原因 | 應該改做 |
|---|---|---|
| **捏造事實** | 權威文件中一個看似合理的猜測，會變成後續每位讀者與 Agent 眼中的「事實」 | 寫 `UNKNOWN — 需要 <負責人> 確認`，並列為未解問題 |
| **捏造商業規則** | 商業規則是決策，由 PM 負責 | 提議一條候選規則，清楚標示，並附上證據 |
| **默默核准決策** | 核准代表當責；AI 無法當責 | 絕不填寫 `approved_by`；絕不自行把權威文件設為 `approved`／`active` |
| **默默修改權威架構** | 架構變更牽涉只有 RD 能承擔的取捨 | 提議 diff，或起草一份取代用的 ADR |
| **抹除決策歷史** | 歷史就是知識（原則 11） | 追加到變更歷史／備註；用取代，而不是刪除 |
| **把原型的假設當成已確認的需求** | 原型是發現需求的工具，不是規格 | 在候選文件中只以 `derived_from` 證據引用原型；把原型的假設列為未解問題 |
| **把實作行為自動視為權威** | 程式碼顯示系統「做了」什麼，而不是「應該」做什麼 | 程式碼與 BR/API 不一致時，向雙方負責人回報 `DRIFT`／`CONFLICT` |
| **自己選邊來解決衝突** | 只有負責人知道哪一邊是錯的 | 引用雙方來源並回報衝突 |
| **成為負責人** | 負責人 ≠ 撰寫者，且負責人必須是能當責的人 | `owner` 一律是 OWNERSHIP.md 中的人類角色 |
| **修改紀錄性知識的原文** | REF 原文是別人的文件；已封存的 CLR／RPT 是已發生的事。改了它就是竄改證據 | 絕不編輯、更名、替換 `_originals/` 中的檔案或已封存的內文；絕不寫入或執行 `seal --reseal`。發現原文有誤 → 寫進 REF 的備註並起草 CLR 向對方確認 |
| **把外部資料或對方的回答直接當成規格** | 客戶文件寫的、對方回答的，是證據；我們要怎麼做是負責人的決定 | 起草 API／BR 的變更提案，以 `derived_from` 引用 REF／CLR，交負責人核准 |

## AI 的撰寫規則

1. **一切都要引用來源。** 權威草稿中每個非瑣碎的陳述，都要指向來源（`FB-003`、`REQ-001#AC2`、`services/x.py:42`）。
2. **明確標示不確定性。** 在行內使用 `UNKNOWN`、`ASSUMPTION` 或 `NEEDS CONFIRMATION (<負責人>)`。絕不把缺口抹平。
3. **最小 diff。** 只改新知識需要改的地方。不要「順便改善」不相關的段落。
4. **尊重知識狀態。** 絕不在未標示為證據的情況下，把探索性內容引入權威文件，也絕不把它當作規則引用。
5. **保留歷史。** 權威文件的每次變更都要新增一列變更歷史。已接受的 ADR 只能追加備註，不能編輯。
6. **表明身分。** 把 `AI` 加入 `authors`。在 PR 描述中說明哪些部分由 AI 產生。

## 上報（Escalation）

當 AI 發現下列任一情況時，應停下來詢問負責人，而不是繼續進行：

- 兩個權威來源不一致。
- 變更會改動已核准的 BR、ADR 或 API 合約。
- 受影響文件的負責人不存在或不明確。
- 某個主張唯一的證據是探索性知識。
- 對某個詮釋的信心很低。

上報的標準輸出是一段簡短、指名負責人的訊息：

```text
NEEDS DECISION (@pm)：BR-001#R2 寫的是 30 天區間；services/recommendation/scoring.py:18 用的是 28。
哪一個才正確？兩邊我都沒有修改。
```
