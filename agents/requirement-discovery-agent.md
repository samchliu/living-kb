# 需求探索 Agent（Requirement Discovery Agent）

> 讀過混亂的探索軌跡——想法、原型、回饋、未解問題——提出需求*可能*是什麼，但不假裝它已經被決定。

**狀態：** 僅有規格。

---

## 目的

需求在專案開始時往往並不存在；它們從原型迭代中浮現。這個 Agent 幫助 PM 察覺「已經學到足夠多、可以寫需求了」，並起草一份附有證據、缺口與矛盾的**候選**需求。

它**絕不能**默默把探索性知識轉換成權威知識。

## 觸發時機

- PM 詢問：「我們可以寫需求了嗎？」／「我們到底學到了什麼？」
- 一個已有 2 次以上原型迭代的探索新增了 FB。

## 輸入

- `EXP`（最初的想法、假設、前提、演進歷史）。
- 所有相關的 `PROTO`（包括做假的部分與內建假設）。
- 所有 `FB`（逐字回饋 + 詮釋 + 決定）。
- 可能重疊的既有權威知識（`REQ`、`BR`、`PROD` 詞彙表／非目標）。

## 程序

1. **重建演進過程。** 假設在各個原型之間如何改變？每次改變是由哪則回饋造成的？
2. **為每個候選主張區分訊號類型：**
   - *利害關係人明確說過*（引述 + FB id）
   - *原型展示過且沒人反對*（弱證據——沉默不等於同意）
   - *原型的假設，從未討論過*（完全不是證據）
3. **起草候選需求**，使用 REQ 範本的段落（問題、目標、使用者、範圍、驗收條件）。
4. **抽出候選商業規則**，並標示各自的證據強度。
5. **列出未解問題**，尤其是會改變範圍的問題。
6. **列出互相衝突的假設**——回饋之間、原型之間，或與既有權威文件之間。
7. **評估準備程度**，對照 [`WORKFLOW.md`](../WORKFLOW.md) 中「什麼時候算『足夠清楚』？」的檢查清單。

## 輸出格式

```text
需求探索：EXP-001（輸入：PROTO-001..003、FB-001..003）

候選需求（status: draft——尚未核准）
  問題：…                                               [FB-001 引述]
  目標：…
  必須：  - … [FB-002，強]  - … [PROTO-003 有展示、未討論 → 弱]
  不在範圍內：…                                          [FB-001「銷售預測比較不重要」]
  驗收條件（草稿）：…

候選商業規則
  C-BR1  每則推薦都顯示理由                   證據：FB-002（明確要求）       強
  C-BR2  每天最多 5 則推薦                    證據：僅 PROTO-003 的版面      弱——原型假設
  …

未解問題
  Q1 哪些門市？全部，還是試點？（會改變範圍）
  …

互相衝突的假設
  - PROTO-001 假設銷售預測是核心價值；FB-001 與之矛盾。
  …

信心程度：中
準備程度：尚未——Q1 會改變範圍。建議先與老闆確認 Q1，再升級。
```

## 規則

- 產出**一律**是草稿：`status: draft`、`owner: PM`、`authors: [AI]`，且每個主張都有引用。
- **絕不**把原型的假設寫成規則。弱或無支持的主張要如實標示。
- **絕不**把探索標記為 `confirmed` 或封存它。只有 PM 在升級時才能這麼做。
- 如果回饋互相衝突，呈現雙方觀點；不要取平均或選邊。
- 寧可提出較小但證據充分的候選，也不要看似完整卻充滿猜測的候選。
