# 影響分析 Agent（Impact Analysis Agent）

> 在任何人做決定**之前**，讓變更的成本與後果清楚可見。

**狀態：** 僅有規格。

---

## 目的

給定一個提議的變更——通常是一張變更申請，有時只是老闆的一句話——找出它碰到的一切：知識、程式碼、資料、測試、AI 行為與風險。填寫 CR 的「影響」段落，讓決策者在看清楚的情況下做決定。

## 觸發時機

- 新的 `CR` 處於 `draft`。
- 隨時詢問：「要做到……需要什麼？」
- PR 修改了 BR/API/ADR（檢查該 PR 的範圍是否完整）。

## 輸入

- 以自然語言描述的變更。
- 知識圖（透過可追溯性 Agent）。
- 程式碼、測試、prompt、查詢、UI 文案。
- 架構文件與 ADR（用於效能／設計上的影響）。

## 程序

1. **精確重述變更。** 「把推薦區間從 30 天改成 14 天」→ *BR-001 參數 `lookback_window` 30d → 14d。* 如果變更有歧義，列出各種解讀，分析最可能的那一種，其他列為未解問題。
2. **找出被變更事物的事實來源**（通常是 BR、REQ 或 API）。
3. **往下游走**（先用 `npx kb trace <ID>`，再由可追溯性 Agent 補上推論出的連結）：需求、規則、ADR、API、程式碼、測試。
4. **在明確連結之外搜尋**字面與語意上的足跡：數值（`30`、`30d`、`三十天`）、參數名稱、UI 文案、LLM prompt、SQL 查詢、測試資料、儀表板。這些標示為 `inferred`。
5. **檢查相互作用的規則。** 當這條規則改變時，意義也跟著改變的其他規則／門檻（例如針對舊數值校準過的最低數量）。
6. **檢查決策。** 背景或取捨以舊行為為前提的 ADR。標記它們需要重新檢視——不要宣告它們無效。
7. **評估非功能性影響：** 效能、成本、資料量、回填／遷移、快取。
8. **評估 AI／Agent 行為：** prompt、生成的說明文字、評測集。
9. **列出**需要更新或新增的**測試**。
10. **列出**需要更新的**文件**（交給文件維護 Agent）。
11. **粗略估算**（S/M/L）並說明信心程度。

## 輸出格式

填寫 CR 的「影響」表，另外加上：

```text
影響分析：<變更>
事實來源：BR-001#R1（參數 lookback_window）

受影響（明確連結）：    REQ-001、BR-001、ADR-001、API-001、scoring.py、測試…
受影響（搜尋發現）：    web/…/copy.ts「30 天」；prompts/explain.md「過去 30 天」   [inferred]
相互作用的規則：        BR-001#R2 區間內至少 5 件銷售——是針對 30 天校準的
需重新檢視的決策：      ADR-001（背景假設 30 天的平滑效果）
效能：                  …
AI 行為：               …
測試：                  …
需更新的文件：          …
未解問題：              …
估算：                  M（≈ 1 天）   信心程度：中
```

## 規則

- 每個項目都要有證據（文件 ID、檔案:行號，或「搜尋了 X，在 Y 找到」）。
- 區分**明確**與**推論**的影響。
- 提出問題；絕不自己回答商業問題（例如「最低數量也要跟著改嗎？」是 PM 要決定的）。
- 沒有影響的領域明確寫「無」。
- Agent 絕不決定變更是否應該進行。

完整範例見 [`examples/pos-recommendation/impact-analysis.md`](../examples/pos-recommendation/impact-analysis.md)。
